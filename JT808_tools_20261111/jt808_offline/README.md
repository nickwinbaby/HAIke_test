# 野猪佩奇专用 · JT/T 808 报文生成与反解V1.2

给 BR_GP02_OBD_808（GD303 / 瑞联 808 协议）用的**单机**报文生成 + 反解工具。
组包、反解、POST 下发都是本地逻辑；**地图绘图与地点搜索需要外网**（高德 / Esri 底图、
Photon 搜索）。不画地图、只用「手动输入方式」时不需要联网。

- **双击 `JT808离线工具.exe` 就能用** —— 一个独立窗口，没有地址栏、没有标签页，
  不用装 Python，不用起服务，不用管跨域。
- 生成的报文你自己通过串口 / 上位机 / 平台侧任意通道下发；也能在窗口里直接
  POST 给平台下发（第 5 分区）—— 桌面版这条链路走本机转发，**不存在 CORS 问题**。
- 适用于设备连不上本机、只想快速拼一条 0x8103 报文发过去验参数的场景。

> 原来「双击 `index.html`」的用法仍然保留，但从浏览器直开时「发送到设备」会被
> 浏览器的跨域策略拦住（见「一之三」）。日常请用 exe。

## 零、桌面版（日常就用这个）

`JT808离线工具.exe` 是单文件程序（约 8.5 MB），页面已经打进 exe 里，
**拷到哪台 Windows 都能直接双击跑**，目标机器不需要 Python、不需要联网装东西。

**使用**

1. 双击 `JT808离线工具.exe`。
2. 等 1～2 秒（单文件程序要先自解压），弹出工具窗口。
   第一次运行 Windows 可能提示「已保护你的电脑」，点 **更多信息 → 仍要运行** 即可
   （exe 没有代码签名，属正常提示）。
3. 顶部是深色导航栏，四个页签：【参数设置】【电子围栏】【终端控制】【报文反解】。
   每个页签只显示本页命令：参数页只有 0x8103/8104/8106，围栏页只有 0x8600~0x8605，
   终端控制页直接给 0x8105 表单，互不串项。页面标题区会随页签切换说明文字。
4. **【下发】不再单列页签**：POST 下发卡片（第 5 分区）已经嵌在三个组包页的右栏，
   生成报文后直接就能发；报文反解页不需要下发，故不显示。
5. 组包、反解、POST 下发三块逻辑与旧版完全一致，只调整了分组与外观。
6. 直接关窗口即退出，后台不残留进程。

**它和浏览器版差在哪**

| | 双击 exe | 双击 index.html |
|---|---|---|
| 窗口 | 独立窗口，无地址栏/标签页 | 浏览器标签页 |
| 第 5 分区发送 | **直接可发**，无跨域限制 | 发不出去；会**自动跳转到 exe**，跳不过去则禁发并提示 |
| 需要 Python | 否 | 否（探到 exe 就用它；只有中转兜底才要） |
| 改页面后 | **刷新窗口即可**（exe 优先读同目录 index.html，且带热重载） | 刷新即可 |

原理是 exe 在本机 `127.0.0.1` 起了一个只服务自己的小 HTTP 服务，页面从那里加载，
于是页面里的 POST 是**同源请求**，由这个小服务替你转发到平台
（`POST /__proxy?u=<真实地址>`）。浏览器那套「JSON 必先 OPTIONS 预检、预检拿不到
`Access-Control-Allow-*` 就整个不发了」的规则，在同源下根本不适用。

> **⚠ 改了页面却还是旧版？** 先看窗口标题栏那一行版本号。
> 老版本 exe 只在启动时读一次页面，进程开着就一直供旧页面；更坑的是
> 双击 exe 时程序会先探测本机有没有实例在跑，探到就直接复用老窗口，
> 连"重启一下"的机会都不给。
> 现在的版本已支持热重载：源 `index.html` 一变，下一次请求（也就是窗口刷新）
> 就自动换成新页面，不用重启 exe。
> 反查办法：日志 `%TEMP%\jt808_desktop.log` 里有一行
> `页面已加载：...index.html（203859 字节）`，字节数对得上就是新页面。

**改默认平台地址**

exe 同目录的 `config.json`：

```json
{
  "platform": "http://10.85.40.3:1813",
  "proxy": ""
}
```

- `platform`：平台地址（只写到端口即可，程序自己拼 `/client/sendRaw`）。
- `proxy`：留空 = **直连，不吃系统代理**。这一点很重要 —— Windows 上程序会默认
  继承 IE/系统代理设置，设备平台在内网，一过代理就是 502。确实要走代理时才填
  `"http://ip:port"`。

改完**重启 exe** 生效。注意 `config.json` 只决定「第一次打开时的默认值」，
在界面上点「改地址 → 保存」改的值存在窗口的本地配置里，优先级更高。

**重新打包**（改了 `index.html` 或 `tools/shared/*.js` 之后必须做）

```bash
cd desktop
E:/python/python.exe build_exe.py
```

需要 `pip install pyinstaller`。产物直接落在上级目录的 `JT808离线工具.exe`。

> 打包脚本会把 `tools/shared/` 一起塞进 exe（包内路径 `shared/`），
> 所以单文件拷到没网、没源码的机器上照样能用。
>
> 只是改页面时**不必**重新打包：exe 优先读同目录的 `index.html` 和 `tools/shared/`，
> 改完刷新窗口即可。只有要把 exe 单独拷走（不带外部文件）时才需要重打。

## 一、怎么用

1. 双击 `JT808离线工具.exe`，等窗口出来。
2. **设备标识**：填 15 位 IMSI，或直接填 12 位手机号。
   下方实时显示实际写进报文的 `BCD[6]` 字节，可以立刻核对对不对。
3. **报文类型**：默认 `0x8103 设置终端参数`。第二组是**电子围栏** `0x8600 ~ 0x8605`
   （设置/删除 × 圆形/矩形/多边形），选中后会切换出对应的电子围栏表单，详见「一之五」。
4. **参数配置 / 电子围栏（分区 3）**：
   - 勾选要下发的参数，填值。
   - 顶部有「服务器快捷填」，填 IP 和端口一键勾上 `0x0013` + `0x0018`。
   - 值有错会当场标红并说明原因（见下方校验规则）。
5. **生成结果（分区 4）**：右侧就是完整 `7E … 7E` 报文。
   - 统计行格式：`总长：51 Byte · 未转义：48 Byte · 消息体：36 Byte · 校验码：0x24 · 消息 ID：0x8103`
   - 「复制报文（无空格）」= `7E81030024…7E`，大多数串口/AT 工具要这种。
   - 「复制报文（带空格）」= `7E 81 03 00 24 … 7E`，方便贴日志、对着字节数。
   - **点任一复制按钮，都会先在下方长出两块预览**：
     上块「复制后待下发（无空格）」、下块「对照（带空格）」，
     各自标注字节数，复制前能先用眼睛核一遍粘出去的是什么。
6. **POST 下发到设备（分区 5）**：把刚生成的 `imei` / `cmd` 直接 POST 给平台，
   由平台向设备下发。详见「一之三」。
7. 下发给设备后，设备会回 `0x0001` 通用应答；查参数则回 `0x0104`。
   把回包粘到 **分区 6「报文反解」** 框，点「解析」。

**页面分区一览**

| 分区 | 内容 |
|---|---|
| 1 | 设备标识（IMSI / 手机号 → BCD） |
| 2 | 报文类型（8103 / 8104 / 8106 / 8105 ＋ 电子围栏 8600~8605） |
| 3 | 参数配置 / 终端控制 / **电子围栏**（按报文类型切换卡片） |
| 4 | 生成结果（报文 + 复制 + 统计） |
| 5 | POST 下发到设备 |
| 6 | 报文反解 |

## 一之二、报文反解的三种粘法都支持

| 写法 | 例子 | 说明 |
|---|---|---|
| 无空格 | `7E81030024…247E` | 直接粘，最常用 |
| 有空格 | `7E 81 03 00 24 … 24 7E` | 中间多少个空格都行 |
| 多条连续 | `7E…7E 7E…7E` 或 `7E…7E7E…7E` | 自动按帧拆分，逐帧独立解析 |

也容忍前面带日志前缀和换行，比如：

```
[11:02:33.441] RX <- 7E0001000511543662165100070023810300F47E
2026-10-30 11:02:33.441 7E UART_RX 7E0001…7E
```

**实现说明**：日志前缀里全是十六进制字符（日期 `2026-10-30`、时间 `11:02:33`），
直接 strip 非 hex 字符会让帧头 `7E` 落在奇偶错位的位置上。所以做法是——
先把文本按「连续 hex 片段」切开（遇到 `[` `R` `X` `<` 这类字符就断），
再在**每个片段内部**找 `7E…7E`，并用消息头里的「消息体长度」字段自校验：
`12 + 分包4 + 体长 + 1校验` 必须恰好等于帧内字节数，自洽才算一帧。
这样多帧、脏前缀、奇偶错位都不会串帧。

### 反解输出（两种视图，可切换）

对齐现场调试习惯的 JSON 格式，字段名保留 `[值]含义` 的写法：

```json
{
  "[7E]开始": 126,
  "[0001]消息Id": 1,
  "消息名称": "终端通用应答",
  "消息体属性对象": {
    "[0000000000000101]消息体属性": 5,
    "版本号": "JTT2013",
    "[bit15]保留": 0,
    "[bit13]是否分包": false,
    "[bit10~bit12]数据加密": "None",
    "[bit0~bit9]消息体长度": 5
  },
  "[115436621651]终端手机号": "115436621651",
  "[0007]消息流水号": 7,
  "数据体对象": {
    "[0023]应答流水号": 35,

```

- 点「表格」切到中文表格视图，同样内容按「帧 / 消息头 / 消息体 / 校验」分区。
- 多帧时每帧上方有标题条：`第 N 帧 · 字节数 · ✓校验通过 · 复制此帧`。
- 校验码会本地复算并给出一致/不一致的结论，不用自己按计算器。

几个解析上的细节：

- **变长列表都有越界保护**：逐个元素检查剩余字节，不够就报「第 N 项越界」并停下，
  不会静默截断或读出垃圾数据；尾部有多余字节会单独标 `✕尾部`。
- **0x0107 比标准多一个「制造商 ID(5 字节)」**——这一点跟固件 `pack_terminal_property_ack()`
  逐字节对齐过，别按只记「型号 20 字节」的印象去数偏移。
- **0x0704 / 0x0400 会递归解析**：每个包体都是完整的 0x0200，直接展开成可读位置字段。
- **0x0108 升级结果**给出的枚举是「终端 / 道路运输证IC卡读卡器 / 卫星定位模块 / 其他」。
- **0x0302 信息点播标志**：`1` 点播、`0` 取消，不是布尔真假的习惯写法。

## 一之三、发送到设备

页面 **第 5 分区「POST 下发到设备」**独立成卡，可以直接把报文 POST 给平台，
由平台再向设备下发 —— 等价于手工开 Postman 发一次。

> **用 exe 的话，这一节下面关于 CORS 的内容可以整段跳过。** 桌面版页面从本机
> `127.0.0.1` 加载，POST 由外壳转发，是同源请求，一次就能发出去，
> 不需要 `send_relay.py`，也不需要平台改任何响应头。
> 下面讲的是「双击 index.html 用浏览器打开」时的情况。

**先确认自己用的是哪个版本**

页面顶部有一条提示条，**只有不是 exe 时才出现**：

- 顶部干干净净、没有黄条 → 桌面版（exe），发送一定发得出去。
- 黄条写着「你现在打开的是网页版（file://）」→ 你双击的是 `index.html`，
  这条发送会被浏览器跨域拦掉，**报文根本没离开本机**。关掉页面改用 exe。

**接口约定**

```
POST http://10.85.40.3:1813/client/sendRaw
Content-Type: application/json

{"imei": "115436621651",  "cmd": "7E81030024…7E"}
   imei = IMSI 后 12 位（必须与报文里的终端手机号一致，工具自动算，不用手填）
   cmd  = 完整 7E…7E 帧，无空格十六进制

平台成功应答：{"code":200,"data":null,"message":"成功"}
平台找不到设备：{"code":2002,"data":null,"message":"客户端不存在"}
```

> **`200` 只代表「平台找到了这个 imei 对应的在线连接并把报文投递出去」，
> 不代表设备已经接受了参数。** 平台对 `cmd` 内容几乎不校验——发残缺帧、空 `cmd`
> 也照样回 `200`。所以「平台说成功但设备参数没变」时，要继续往下查设备侧
> （看设备有没有回 `0x0001` 通用应答、应答结果码是不是 0）。
> 而 `2002 客户端不存在` 则一定是 **imei 填错 / 设备没连到这个平台**，
> 报文根本没发出去。

**界面行为**

- 发送前能在 `imei` / `cmd` 两行**预览实际要发的内容**，确认无误再点。
- 点「发送到设备」→ 弹窗提示结果；成功显示 `下发成功`，
  业务失败显示 `下发失败（code 500）` 并把平台 `message` 原样透传。
- 弹窗关掉后，结果仍保留在发送区下方，方便回看。
- 地址和超时可改，点「保存」写进 `localStorage`，下次打开还在。
- 没生成报文 / IMSI 非法时，发送按钮是**禁用**的，不会发出空载荷。
- 按钮旁的圆点显示**发送通道状态**：exe 下恒为绿「内置转发已就绪」；
  网页版下显示「未接本机工具，发不出去」（此时发送按钮同时被禁用）。
- 网页版启动时会自动探测本机 `18099~18105`，探到 exe 就整页跳过去。

**为什么 Postman 能发、工具发不出去**（实测结论，2026-11-04 复测）

| 现象 | 实测结果 |
|---|---|
| Postman / curl POST `application/json` | HTTP 200（真设备回 `code 200`；imei 不存在回 `code 2002 客户端不存在`） |
| 浏览器直连同一地址 | `Failed to fetch`，控制台报 CORS |
| 浏览器 `OPTIONS` 预检 | **HTTP 200 + `Allow: POST,OPTIONS`，但没有任何 `Access-Control-Allow-*` 响应头** |
| 换 `text/plain` 绕开预检 | **HTTP 415**，平台只认 `application/json` |

> 10-30 那次测到 OPTIONS 回 **403**，11-04 复测变成 **200 但仍无 CORS 头**（网关配置换过）。
> 两种都过不了预检，**结论不变，但原因不是"平台回 403"**。

浏览器发 `application/json` **必先发 `OPTIONS` 预检**，预检要求响应里带
`Access-Control-Allow-Origin` / `Allow-Methods` / `Allow-Headers`，平台一个都不给，
预检不通过，浏览器于是**根本不发 POST**；而平台只接受 `application/json`，绕不过去。
同样的缺头也让「POST 已到平台、但浏览器读不到返回体」。
Postman 是普通 HTTP 客户端，不执行 CORS，所以能成功。**这跟报文、imei 都没关系。**

**"用一阵子突然发不出去"不是 CORS**

CORS 是平台侧固定配置：通就一通到底，不通就从头就不通，**不会随时间变化**。
出现"连一段时间后再发就不通"，真实原因通常是下面两类，而它们在浏览器里表现**完全一样**，
都只是 `Failed to fetch`：

1. **平台侧会话/网关**：登录态过期、IP 白名单、限流，实际回了 403，但响应不带 CORS 头，
   浏览器照样只报 `Failed to fetch`；
2. **设备 808 链路断了**：平台查不到该 imei 的在线连接，回 `{"code":2002,"message":"客户端不存在"}`
   （工具会翻成「平台找不到该设备」），报文接口本身是通的。

→ 想区分到底卡在哪一层，只有一条路：**走本地中转，看它打印的 HTTP 状态码和响应体**。

**发送通道的选择顺序**

1. **双击 exe（唯一推荐）**：页面由本机服务提供，发送走同源 `/__proxy`，与跨域无关，永远可发；
2. **网页版，但 exe 已经在跑**：本页启动时会自动探测本机 `18099~18105`，
   探到就整页跳到 exe 的地址 —— 用户什么都不用做，也不用关心端口；
3. **网页版，exe 没在跑**：顶部横幅提示 + **发送按钮直接禁用**（不让点了才失败），
   横幅上有「我已启动，重新检测」；
4. `send_relay.py`（`127.0.0.1:8099`）保留为**没装 exe、只有网页**时的兜底，
   命令行起来后页面会自动改走它。

> **2026-11-04 行为变更**：以前网页版是"先试直连 → 被 CORS 拦 → 再自动兜底中转 → 再报一长串原因"，
> 用户每次都要先吃一次 `Failed to fetch` 才看到提示，而且提示里教人敲 `python send_relay.py`。
> 现在改成**启动即探测 + 探不到就禁发**，把死路提前堵掉：发得出去才让你点，发不出去直接告诉你双击 exe。
> 同时 exe 改为**优先读同目录的 index.html**，改页面不用再重新打包。
一劳永逸的办法是让平台给 `/client/sendRaw` 加上 `Access-Control-Allow-Origin`、
`Allow-Methods: POST`、`Allow-Headers: Content-Type` 并放行 `OPTIONS`，那样直连就能通。

## 一之四、发不出去时先跑诊断，别猜

「点了发送没反应」有三种完全不同的原因，处置方式也完全不同，靠猜会浪费很多时间。
本目录附带 `diagnose.py`，从下往上逐层探，每层给硬证据，最后给一个明确结论：

```bash
python diagnose.py
# 换目标：
python diagnose.py --host 10.85.40.3 --port 1808 --path /client/send
# 真实下发一次（会真的下指令给设备，故默认关闭）：
python diagnose.py --send --imei 115436621651 --cmd 7E8103…7E
```

| 层 | 探什么 | 不通说明什么 |
|---|---|---|
| 1 DNS | 域名能否解析 | 地址写错 / DNS 不可用 |
| 2 TCP | 三次握手、耗时 | 服务没起 / 路由不通 / 端口错 |
| 3 裸 HTTP | 握手后发最小 GET，看有无字节 | **应用层被拦**（关键层） |
| 3.5 私有协议 | `--payload-hex` 灌原始字节 | 端口是不是 JT808 等私有协议 |
| 4 POST 探测 | 空 body 打接口，看有无状态码 | 接口存在但拒绝 / 不存在 |
| 5 真实下发 | 用真实 imei + cmd 下发 | 业务链路是否真的通 |

**结论标签**：`A` DNS 失败 / `B` TCP 不通 / `C` 握手劫持 / `D` 应用层半通 /
`E` 接口正常 / `F` 平台明确回「设备不在线」/ `G` 端口活着但不是 HTTP。

**为什么第 3 层最重要，以及它必须区分两种「0 字节」**：

TCP 握手成功只证明「有东西回了 SYN-ACK」。同样是「HTTP 请求后收到 0 字节」，
却有两种完全不同的成因，混淆会直接导致误判：

| 现象 | 含义 | 处置 |
|---|---|---|
| 对端**主动 FIN/RST** | 那里**真有服务**在跑，它按自己的协议解析了你的数据并判定非法断开 | 换成该协议去谈（`--payload-hex`），别用 HTTP |
| 连接被**吊住直到超时** | 防火墙/边界设备代答了握手并吞掉后续所有包 | 找 IT 放通 |

前者说明端口是活的 —— 这就是 `G` 标签。典型例子：`1808` 是 **JT808 设备接入端口**
（设备自己连上来注册上报），往里 POST JSON 不会得到任何应答，但它确实是通的；
而 Web 接口（`/client/send` 这类）通常在 `80/443` 上。
**「设备接入端口」和「Web 接口端口」是两回事**，发指令要打后者。

如果端口回 0 字节且一直吊着，才会判 `C`（劫持）。据此还能解释一个常见困惑：
`10.85.40.3:1808` 判 `C` 而 `xatst.richlinkcloud.com:1808` 判 `G` —— 前者确实被
网络边界拦了，后者端口本身是好的，只是它不讲 HTTP。

> 设备关机不会让 HTTP 接口无响应。接口在平台侧，设备离线时平台照样会回
> `{"code":500,"message":"设备不在线"}`。
> 所以：**接口层完全无响应 = 网络/防火墙问题；接口回「不在线」 = 设备侧问题。**
> 这两件事必须分开看，`diagnose.py` 就是做这个区分的。

## 一之五、电子围栏 `0x8600 ~ 0x8605`

报文类型第 2 组 6 个按钮，选中后左栏分区 3 切换成电子围栏表单。
字段格式与固件 `srv_geo_fence_808.c` 逐字节对齐。

| 报文 | 形状 | 消息体 |
|---|---|---|
| `0x8600` | 设置圆形 | `[操作1][区域总数1]` + `[ID4 属性2 纬度4 经度4 半径4 (+起止12) (+限速3)]` |
| `0x8601` | 删除圆形 | `[区域总数1][ID4 × n]`，n=0 删全部 |
| `0x8602` | 设置矩形 | `[操作1][区域总数1]` + `[ID4 属性2 左上纬4 左上经4 右下纬4 右下经4 (+12) (+3)]` |
| `0x8603` | 删除矩形 | 同 `0x8601` |
| `0x8604` | 设置多边形 | `ID4 属性2 (+12) (+3) 顶点数2` + `顶点(纬4 经4) × n` —— **无操作/总数前缀** |
| `0x8605` | 删除多边形 | 同 `0x8601` |

### 围栏绘图（V1.2 改版）

点电子围栏卡片里的「绘制围栏」，先选一种方式：

| 方式 | 说明 |
|---|---|
| **绘图方式** | 打开 Leaflet 在线地图，像 808 平台一样圈圆 / 矩形 / 多边形；滚轮缩放、地点搜索定位、可连续画多个、可删第几个或全部；点「确定并回填」把第 1 个图形写进数字输入框，一条 0x8600 / 0x8602 报文按全部同形状图形组包 |
| **手动输入方式** | 回到原来的数字表单，直接填经纬度 / 半径 / 顶点，含「按中心点 + 半径」自动算点 |

- **底图需要外网**：低缩放用 Esri 全球图，高缩放用高德路网，搜索走 Photon（免 key）。
  瓦片加载失败会在地图上明确提示；此时请改用「手动输入方式」。
- 坐标统一按 `GCJ-02 → WGS84` 反算后写进报文，与设备上报坐标系一致。
- 地图代码抽到 `tools/shared/jt808_map.js`，与 `jt808_tracker` 平台**共用一份**；
  Leaflet 是本地 `vendor/` 文件，不走 CDN。
- 单帧区域数上限 10 项（固件 `JT808_GEO_FENCE_MAX_NUM`），超出会提示分批下发；
  0x8604 多边形按协议一帧只能带 1 个区域，画了多个同样提示分批。
- 点「清空图形」或选「手动输入方式」会清掉地图上画的围栏，报文回到单区域手工字段。
- 旧版自绘 Canvas 经纬网格已退役，不再提供离线网格回退。

**矩形 / 多边形各有两种填法，用小按钮切换**

卡片里是一排两段按钮，同一时刻只显示当前方式的输入框，两套不会混在一起：

- **手工填两角 / 手工填顶点**：直接填左上/右下，或直接编辑顶点列表，适合从地图上量出来的坐标。
- **按中心点 + 半径**：填中心经纬度和半径，点「算两角并填入」/「生成顶点并填入」，
  工具算好后**自动切回手工模式**，可以立刻核对数值、继续微调。
  - 矩形：半径 = 中心到边的距离，得到 `2R × 2R` 的正方形，按「左上=西北、右下=东南」写。
  - 多边形：半径 = 中心到顶点，从正北起顺时针生成正 n 边形（顶点数 3~10）。
  - 换算是小范围平面近似：纬度 1 度 = 111320 米，经度 1 度 = 111320 × cos(纬度) 米。
    300 米以内的偏差在 1 米量级，远小于 GPS 自身误差，自测用足够。

**几个容易踩的点**

- **操作字段**：`0` 更新（先清空同类全部区域再写入，**会删掉已有区域**）、
  `1` 追加、`2` 修改（按 ID 覆盖）。默认 `0`，只想加一条时请改成 `1`。
- **`0x8604` 没有操作/区域总数前缀**，标准如此，固件也是这么解析的。
- **区域属性位**：`bit0` 起止时间、`bit1` 限速、`bit3` 进区域报警给平台、
  `bit5` 出区域报警给平台。`bit3`/`bit5` 都不勾时区域照样保存，但设备**不会**
  发 `0x0200` 的 `0x12` 附加项，等于没有报警。
- **经纬度按度填**（如 `31.230416`），工具换算成 1e-6 度整数；
  纬度 ±90、经度 ±180，负值按 32 位补码写出。
- **时间字段**是起 / 止各 6 字节 BCD `YYMMDDhhmmss`，勾了 `bit0` 就固定占 12 字节。
  点框弹系统日历（精确到秒），框下方小字是实际发走的 12 位 BCD 及其 UTC 折算。

  **固件对时间只做一条判定**（`geo_fence_time_in_range()`，`srv_geo_fence.c:190`）：

  ```c
  return utcTime >= startUtc && utcTime <= endUtc;   /* 闭区间，秒级 */
  ```

  没有「必须整点」「必须晚于下发时刻」这类要求，**唯一的实质约束是当前这一刻
  要落在 `[起始, 结束]` 之内**，否则 `timeValid=false`，进出方向都不报警。
  由此推出四条硬要求：

  | # | 要求 | 违反后果 |
  |---|---|---|
  | 1 | 起止**都**得是完整合法日期（年/月/日都不能为 0） | `jt808_bcd_gmt8_to_utc_timestamp()` 见 `month < 1` 直接失败 → 时间恒无效 → 永不报警 |
  | 2 | 结束时间必须在**未来** | 过了 `end` 永不报警，且事后不补报 |
  | 3 | 起止不能写反（`start > end`） | 完整日期分支**不支持跨零点**，比较恒 `false` |
  | 4 | 日期要真实存在（如 `0230`） | 解析期能过（只查 1~31），算时间戳时 `days_in_month` 校验失败 → 恒无效 |

  - ⚠️ **全 0 不是「不限时段」**：`jt808_geo_fence_valid_bcd_time()` 会放行全 0，
    且 `geo_fence_time_in_range()` 里只有**起止前 3 字节都为 0** 才进「每天只比时分秒」
    分支；实际效果是每天 `00:00:00` 那一秒算在时段内 —— 等于围栏永不报警。
    **只写一边全 0（如 start `000000000000`、end 合法）更糟**：不走 daily 分支，
    `month=0` 直接判无效。不想限时段就**别勾 `bit0`**。
  - ⚠️ **时区取决于固件版本，填之前先确认设备跑的是哪版**：
    - **按北京时间解释**（`br_GP02_GT117_YK`，函数 `jt808_bcd_gmt8_to_utc_timestamp()`）：
      实现是 `... - 28800`（`srv_geo_fence.c:145`），
      即北京 `11:06:48` 折成 UTC `03:06:48` 再参与比较。
      **注意方向是减不是加**：换算只是把填报值翻译成 UTC，窗口长度不变，
      不会因此「多出 8 小时」而免于过期。
    - **按 UTC 解释**（`br_GP02_OBD_808`，函数 `jt808_bcd_to_utc_timestamp()`，
      `srv_geo_fence.c:144` 直接 `days*86400 + h*3600 + m*60 + s`）：
      **不做任何偏移**，填进去的就是 UTC，想让北京 `11:06` 生效得填 `03:06`。
      ⚠️ **303 项目（`00_br_GP02_OBD_808_1027`）跑的就是这版** ——
      填 `261102110648` 实际是北京 `19:06:48` 才结束，比你以为的**晚 8 小时**。
    - ⚠️ **同一帧在两版上的判定可能相反**：`261102110648` 这帧，GT117_YK 版窗口是
      UTC `03:00:00 ~ 03:06:48`（北京 11:06 就结束）；OBD_808 版窗口是
      UTC `03:00:00 ~ 11:06:48`（北京 19:06 才结束）。而设备 `utcTime` 是 GPS 给的
      真实 UTC，**不随固件版本变** —— 所以「过没过期」必须落到具体版本上算。
    工具蓝字两种对照都给了，按设备实际版本取对应那一句即可。
    判定时用的是上报定位里的 `utcTime`，与设备 RTC 是否校准直接相关。
  - ⚠️ 这是**绝对日期区间**，过了结束日期就永不再报警，要长期生效必须重新下发
    （做法：把 `end` 直接设到年底，如 `261231235959`）。
  - ⚠️ **时段外的状态翻转会被吃掉**：`srv_geo_fence_check()` 里
    `currFence->node.lastState = state;` 写在 `switch` **之外**、无条件执行，
    `timeValid=false` 只是跳过发报警。所以「时段外把车开出圈、时段内停在圈外」
    不会补报 —— 整次进出必须都在时段内完成。
  - **前两位是年份，不是世纪**：`2026-10-30 07:30:00` → `261030073000`。
    `202610300730` 会被当成 26 月，固件回 `0x0001` 结果码 `2 消息有误`。
  - 年月日写 0、时分秒非 0（如 `000000073000`）**固件同样拒收**（月份 `00 < 01`），
    工具会拦住，不会组出必被拒的帧。
- **`0x0001` 结果码**：`0 成功(Success)` / `1 失败(Failure)` /
  `2 消息有误(MessageError)` / `3 不支持(NotSupported)` / `4 报警处理确认`。
  结果为 `2` 且被应答的是 `0x8600~0x8605` 时，反解会直接给出排查方向。
- **固件上限**：单条设置报文最多 10 项（`JT808_GEO_FENCE_MAX_NUM`）、
  删除最多 40 个 ID（`GEO_FENCE_MAX_NUM`）、多边形 3~10 个顶点、
  ID 和半径都不能为 0，多边形相邻顶点不能重复。
- 工具当前**每条报文只生成 1 个区域项**（区域总数 = 1）。要批量下发多区域，
  改代码里的 `collectFence()` 或分多次发。

### 围栏报警怎么在日志里认

设备**没有**单独的"围栏报警"消息，报警是搭在 `0x0200` 位置汇报上带出去的：

| 位置 | 内容 |
|---|---|
| 报警标志 DWORD `bit20` | 置 `0x00100000`（进出区域报警） |
| 附加项 `0x12`，6 字节 | 位置类型 1B（1 圆 / 2 矩形 / 3 多边形 / 4 路线）+ 区域 ID 4B + 方向 1B（**0=进，1=出**） |

把带 `0x12` 的 0200 粘进本工具第 6 分区，会解成
`圆形 区域 ID=1，进区域（方向值 0）`，报警位一栏同时列出 `进出区域`。

关键日志（`srv_geo_fence.c` → `gsw_gps.c` → `gsw_modem_protocol_convert.c`）：

| 日志关键字 | 含义 |
|---|---|
| `[geo-fen] check circle, id .., cur state ..` | 每轮定位都打，`state` 1=圈内 0=圈外 |
| `[geo-fen] enter warning report` | 判定进区域，且 bit3 允许、时间窗内 |
| `[geo-fen] exit warning report` | 判定出区域（对应 bit5） |
| `808 geo fence alarm enqueue id:.. type:.. direction:.. count:..` | 已入告警队列，等下一帧 0200 带走 |
| `808 geo fence extra: type=.. id=.. direction=..` | 组 0200 时真的填了 0x12 附加项 |
| `808 geo fence alarm bind 0x0200 seq:..` | 报警绑到这条 0200 的流水号，等平台确认 |
| `808 geo fence alarm confirmed by 0x0200 seq:..` | 平台 `0x8001` 应答对上，报警出队 |
| `808 geo fence alarm confirm timeout, retry id:..` | 30 s 没确认，2 s 后重发 |
| `808 geo fence alarm dropped, location not found id:..` | 围栏在判定后被删，告警丢弃 |
| `808 geo fence alarm queue full, drop id:..` | 队列满（上限 8）丢弃 |

四个容易误判的点：

- 报警只在**状态翻转**时产生（外→内 / 内→外），一直待在圈内不会重复报。
- **设置成功后第一次检测只记账、不报警**：`srv_geo_fence_check()` 里
  `lastState == POS_OUTSIDE` 才报进、`== POS_INSIDE` 才报出，而新建/修改后的节点
  `lastState` 被置成 `POS_UNKNOWN(2)`，与两者都不等。所以「设完马上开走」不会出报警，
  必须**至少检测到一次真实状态**（打 `[geo-fen] check circle .. cur state x`），
  之后发生翻转才报。
- 前提是 `bit3`/`bit5` 至少勾一个；都不勾区域照样保存，但永远不产生报警。
- 平台 `0x8001` 的应答流水号必须对上那条 0200，否则设备会持续重发带 0x12 的 0200 直到超时重试。

两个容易被当成"设备抽风"的行为：

- **报警时可能多一条 0200**：`srv_geo_fence_808_need_immediate_report()` 会在告警入队后
  立刻触发一次上报，不等配置的周期，所以日志里会出现「比周期更密」的 0200。
- **断网时只写一次盲区就放弃**：`srv_network_get_frame_connect_state() == SERVER_DISCONNECT`
  时，`srv_geo_fence_808_clear_alarm()` 直接清队列，不会等恢复后补报。

### 怎么造出一次真实报警（现场验证 SOP）

**先分清两个「周期」，别混**：

| 环节 | 周期 | 代码 |
|---|---|---|
| 围栏**判定** | `geoFenceCheckInterval`，默认 **60 s**，未到直接 return | `gsw_gps.c:2799` |
| 报警**上报** | **立即**，告警入队后下一个 1 s 节拍就组 0200，不等上报周期 | `gsw_gps.c:1863` → `srv_geo_fence_808_need_immediate_report()` |

也就是说「设完围栏立刻要报警」做不到，卡的是**检测**这一步，不是上报；
一旦判定翻转，0200 最迟 1 s 就出去（正常周期报文默认 10 s 一条）。

判定发生在 `srv_geo_fence_check()`，一句话概括：

```
当次 state != 上次 lastState  →  才可能报警
└ 进：state=1 且 lastState=0     └ 出：state=0 且 lastState=1
```

而 `lastState` 在下发 `0x8600~0x8605`（操作 0/1/2 都一样）时会被重置成
`POS_UNKNOWN(2)`，**跟 0 和 1 都不等**。所以「设完围栏立刻开走」必然不出报警，
第一次检测只是把状态记下来。

**四个前提，缺一个都白测**

| 前提 | 检查点 | 不满足的表现 |
|---|---|---|
| GPS 已定位 | `bsl_gps_get_location_status()` 为真 | `gsw_geo_fence_check_handle()` 直接 return，日志连 `[geo-fen] check` 都没有 |
| 平台在线 | `0x0200` 能正常上报 | 告警入队后立刻被 `clear_alarm()` 清掉 |
| 属性 `bit3` 或 `bit5` 置位 | 测试用 `0x0028`（进+出，不限时段） | 区域能存、但永不产生 `0x12` |
| 半径够大 | ≥ 300 m | GPS 自身误差 5~10 m，填 1~2 m 等于让车「精确踩点」 |

**步骤（先做出区域报警）**

| 步 | 动作 | 要看到的 |
|---|---|---|
| 1 | 可选，把检测间隔 60 s 改成 8 s：`0x8103` 参数 ID `0x04390000`、U32=8（范围 8~84600） | `0x0001` result=0；`0x8104` 回读 |
| 2 | 中心点填**车当前位置**，半径 `500`，属性 `0x0028`，操作 `0` | `0x0001` result=0，日志 `0x8600 parse success: operation=0 count=1` |
| 3 | 等 ≥1 个检测周期（改过参数就 8 s，否则 60 s） | `[geo-fen] check circle, id 1, cur state 1` ← 已记成「圈内」 |
| 4 | 开车离开 500 m 以上 | 下个周期 `cur state 0` |
| 5 | —— | `[geo-fen] exit warning report` → `808 geo fence alarm enqueue id:1 type:1 direction:1 count:1` → `808 geo fence alarm extra: type=1 id=1 direction=1` → `808 geo fence alarm bind 0x0200 seq:...` |
| 6 | 平台侧收 `0x0200` | 报警标志含 `0x00100000`，附加项 `0x12` = `01 00000001 01`（圆 / ID1 / 方向1=出） |
| 7 | 平台回 `0x8001` 对上那条 0200 | `808 geo fence alarm confirmed by 0x0200 seq:...` |

要**进**区域报警就把第 3、4 步对调：先让车待在圈外、等到 `cur state 0`，再开进圈内。

**无实车自测（拿设备本身当车）**

思路可行，但**半径不能取 1 m**——那样会把方向搞反：

- 新设围栏的 `lastState = POS_UNKNOWN`，第一次检测只记账。半径 1 m 时，GPS 抖动
  （2.5~10 m CEP）几乎必然让第一次判定就是「圈外」，于是 `lastState` 被记成 `0`，
  之后你再怎么挪都还是 `0`，**永远等不到「出区域」报警**，只会偶然跳出一次「进区域」。
- GPS 的分辨率：`1e-6` 度 ≈ 0.11 m（纬）/ 0.09 m（经，34°N），桌面挪几十厘米坐标根本不变。
  要产生可辨识位移，**至少移动 20 m**，建议 80~100 m。

推荐做法：先用 `0x8201` 查设备**当前**坐标（别用平台缓存的老坐标），
半径取 30~50 m、属性 `0x0028`，等一轮看到 `cur state 1`（确认圈住了设备），
再拿着设备走出 80 m 以上，下一轮就是 `cur state 0` → 出区域报警。

只能在室内/桌前时，半径取 5~10 m 靠漂移翻转也能触发，但属于碰运气：
必须先看到过 `cur state 1`，再从 `1` 变 `0` 才算一次「出区域」。
如果连 `[geo-fen] dev pos ..` 都不打，就是没定位，换到窗边或室外再试。

⚠️ **平台每保存一次围栏就重下发一次 `0x8600`**，`lastState` 就再归 `POS_UNKNOWN`。
如果日志里 `0x8600 parse success` 每隔一会儿就刷一次，说明平台在反复下发，
那无论车怎么动都等不到翻转——先掐掉平台的重下发再测。

## 二、参数校验规则（与固件逐条对齐）

校验逻辑对齐 `gsw_modem_validate_set_param_item()`（`gsw_modem_protocol_convert.c`），
**工具放行的报文，固件一定不会因参数非法整帧拒绝**。

| 参数 | 类型 | 规则 | 固件依据 |
|---|---|---|---|
| 0x0001 终端心跳间隔 | DWORD | 10 ~ 3600 秒 | 同 |
| 0x0010 主服务器 APN | STRING | 1 ~ 31 字节 | `ucLen < STRING_PARAM_LEN(32)` |
| 0x0011 拨号用户名 | STRING | 0 ~ 31 字节，可为空 | 空值固件落盘为 `"NULL"` |
| 0x0012 拨号密码 | STRING | 0 ~ 31 字节，可为空 | 同上 |
| 0x0013 主服务器地址 | STRING | 1 ~ 63 字节，**禁止 `:` 和 `;`** | 协议 9.1 第 6 条 |
| 0x0018 服务器 TCP 端口 | DWORD | 1 ~ 65535 | 同 |
| 0x0029 缺省汇报间隔 | DWORD | 8 ~ 1800 秒 | 同 |
| 0x0083 机动车号牌 | STRING | 1 ~ 20 **字节** | 中文按 GBK 双字节计 |
| 0xF001 当前仪表里程基准 | DWORD | 0 ~ 42949672（单位 **0.1 km**） | `value*100` 换米不得溢出 u32，固件同规则 |

补充约束：

- **一次最多 9 项** —— 固件 `JT808_PARAM_ITEM_MAX = 9`，超了整帧拒绝。
- **同帧不允许重复参数 ID** —— 固件会整帧拒绝（最终值不明确）。
- **0x0013 不能写 `host:port`** —— 端口必须单独用 0x0018 下发。
  这是上一版移植特意改掉的旧行为，别写回去。
- **0xF001 是自定义参数（协议表12）** —— 标准 JT/T 808 参数表里没有这个 ID，
  平台工具若只列标准参数则看不到它，需手发 0x8103 或在本工具里勾选。
- 未列出的参数 ID（0x0014~0x0017 备份服务器等）固件当前**未实现**，
  工具不提供，避免生成注定失败的报文。

## 三、几处容易踩的坑

**1. 终端手机号不是 IMEI**
协议 9.1 第 8 条：取 SIM 卡 **IMSI 后 12 位**，直接 BCD 编码，不补位、不截断到别的长度。
填 15 位 IMSI 工具会自动取后 12 位；填 12 位则原样用。
工具只认这两种长度，其它长度（比如 20 位 ICCID）会直接报错，防止稀里糊涂编错。

**2. 中文车牌要按 GBK 编码**
工具内置 GBK 编码器（靠 `TextDecoder('gbk')` 反查构造），直接输入「京A12345」即可，
自动编成 `BE A9 41 31 32 33 34 35`（8 字节）。
长度上限 20 是**字节**不是字符，10 个汉字正好卡满。
如果遇到 GBK 编不了的生僻字，用 `hex:` 前缀直接给字节，例如 `hex:BE A9 41`。

**3. 消息体跨 0x7E / 0x7D 必须转义**
值里出现 `0x7E` 就会破坏帧边界，工具已自动转义成 `7D 02`；`0x7D` → `7D 01`。
复制「报文」拿到的就是转义后的，别再手动处理一遍。

**4. 流水号**
设备侧通常会对重复流水号做丢弃处理。连续下发多条时，请手工把「消息流水号」
改大一点（或点旁边的「换一个」），不要把同一帧连发两次。

**5. `0x0200` 未定位时经纬度也可能非 0**
状态位 bit1=0 表示**当前没定位**，但固件此时上报的是最后一次有效位置
（读 `AGPS_INFO_FILE`），高程/速度/方向填 0。所以看到「未定位 + 有坐标」不是解析错了，
判位置有效与否要看 bit1，不能看坐标是不是 0。

## 四、消息体格式速查

**0x8103 设置终端参数**
```
参数总数(1) + N × [ 参数ID(4, 大端) + 参数长度(1) + 参数值(长度字节) ]
```

**0x8106 查询指定终端参数**
```
参数总数(1) + N × 参数ID(4, 大端)      // 只勾 ID，不用填值
```

**0x8104 查询全部参数**
```
（空消息体）
```

**0x8001 平台通用应答**
```
应答流水号(2) + 应答消息ID(2) + 结果(1)
```

**0x8105 终端控制**
```
命令字(1) + [命令参数(STRING)]          // 只有命令字 1 / 2 / 0xF0 带命令参数
```
- 命令字：`1` MCU 升级 / `2` 连接指定服务器 / `3` 关机 / `4` 复位 / `5` 恢复出厂 / `0xF0` Modem 升级
- 命令参数按命令字取值，半角「;」分隔、GBK 编码，无值的字段留空但**分隔符必须保留**：
```
1 / 0xF0（11 字段）
  URL地址;拨号点名称;拨号用户名;拨号密码;地址;TCP端口;UDP端口;制造商ID;硬件版本;固件版本;连接到指定服务器时限
  · UDP 端口固定留空（本协议不用 UDP），两侧分号不能省
  · 硬件版本填 Modem 当前版本，须与 0x0107 一致
  · 固件版本：命令字 1 填目标 MCU 版本，0xF0 填目标 Modem 版本

2（9 字段）
  连接控制;平台鉴权码;拨号点名称;拨号用户名;拨号密码;地址;TCP端口;UDP端口;连接到指定服务器时限
  · 连接控制 = 1 时整串只填 "1"，其后无任何参数
3 / 4 / 5：无命令参数
```
- 协议里的命令字 `6`（关闭数据通信）/ `7`（关闭所有无线通信）固件侧只回成功不执行动作，工具不再提供，反解仍能识别。

**0x8600 设置圆形区域 / 0x8602 设置矩形区域**
```
操作(1) + 区域总数(1) + N × [
  ID(4) 属性(2)
  // 圆形：纬度(4) 经度(4) 半径(4)
  // 矩形：左上纬度(4) 左上经度(4) 右下纬度(4) 右下经度(4)
  [起止时间 BCD[6]×2]   // 属性 bit0
  [最高速度(2) 超速持续(1)] // 属性 bit1
]
```
**0x8604 设置多边形区域**（无操作/区域总数前缀，单条）
```
ID(4) 属性(2) [时间12] [限速3] 顶点数(2) + N × [纬度(4) 经度(4)]   // N = 3~10
```
**0x8601 / 0x8603 / 0x8605 删除区域**
```
区域总数(1) + N × ID(4)               // 总数 0 = 删除全部同类区域
```

**0x0200 位置信息汇报**（仅反解，生成侧不提供——这条是设备上报的）
```
报警标志(4) 状态(4) 纬度(4) 经度(4) 高程(2) 速度(2) 方向(2) 时间BCD[6]
+ N × [ 附加项ID(1) 长度(1) 内容(长度) ]        // 从第 29 字节起，无结束标记，读到尾部为止
```
- 纬度 / 经度是 **1e-6 度**的 32 位整数，北纬东经为正；
- 速度单位 **0.1 km/h**，高程单位米，方向 0~359（正北 0，顺时针）；
- 状态位 bit0=ACC、bit1=定位、bit2=南纬、bit3=西经，其余位含义见工具内 `LOC_STATUS_BITS`；
- 附加项按 TLV 循环解析，长度越界会直接报错而不是静默截断。

附加项取值（协议表 27，工具反解按此换算，无效值直接标「无效」）：

| ID | 长度 | 含义 | 换算 |
| --- | --- | --- | --- |
| 0x01 | 4 | 里程 | DWORD ÷10，km |
| 0x02 | 2 | 油量 | WORD ÷10，L |
| 0x03 | 2 | 车速 | WORD ÷10，km/h |
| 0x07 | 2 | 动力电池 SOC | WORD ÷10，% |
| 0x12 | 6 | 进出区域报警 | 类型(1)+区域ID(4)+方向(1) |
| 0x30 | 1 | 信号强度 | 0~100 |
| 0x31 | 1 | GNSS 卫星数 | 颗（未定位/无卫星时固件填 0，不是 0xFF） |
| 0xE1 | 4 | 设备累计里程 | DWORD ÷10，km（含 0xF001 基准） |
| 0xE2 | 2 | 剩余油量百分比 | WORD ÷100，%，无效 0xFFFF |
| 0xE3 | 2 | 发动机转速 | WORD，RPM，无效 0xFFFF |
| 0xE4 | 1 | 动力电池 SOH | BYTE，%，无效 0xFF |
| 0xE5 | 2 | 主电电压 | WORD ÷10，V，无效 0xFFFF |
| 0xE6 | 2 | 冷却液温度 | 值 −40，℃，无效 0xFFFF |

> 0xE6 协议表 27 定义 WORD（2 字节），固件已按 WORD 上报；工具同时兼容 1 字节旧报文。

**0x0107 查询终端属性应答**（仅反解）
```
终端类型(2) 制造商ID(5) 终端型号(20) 终端ID(7, BCD) SIM卡ICCID(10, BCD)
+ 硬件版本号长度(1) + 硬件版本号
+ 固件版本号长度(1) + 固件版本号
+ GNSS模块属性(1) 通信模块属性(1)
```
- **制造商 ID 这 5 字节别漏**，漏了后面全部偏移错位（会看到 ICCID 只剩 19 位这种怪现象）；
- 终端型号 / 制造商 ID 是定长 ASCII，尾部补 `0x00`，工具已去掉补位再显示；
- GNSS 属性按位：bit0 GPS、bit1 北斗、bit2 GLONASS、bit3 Galileo；
- 通信模块属性按位：bit0 GPRS、bit1 CDMA、bit2 TD-SCDMA、bit3 WCDMA、bit4 HSDPA、bit5 LTE；
- 实测设备（GD303 + EG915）回报 `0F 20`，即「四星座全支持 + LTE」。

**帧结构**
```
7E | 消息ID(2) 消息体属性(2) 终端手机号BCD[6] 流水号(2) | 消息体(n) | 异或校验(1) | 7E
```
消息体属性低 10 位 = 消息体长度。

  时间说明压缩成一行且不再重复全 0 那一段
- **BCD 时间语义校验**（与固件 `jt808_geo_fence_valid_bcd_time` 一致）：
  全 0 合法、`261030073000` 合法、`202610300730`（月份 26）、月 00/13、
  日 00/32、时 24、分 60、秒 60、非数字逐条被拒，且报错文本带出正确写法
- **0x0001 结果码**：中英双语、`result=2` 围栏类给时间格式提示、
  非围栏类给通用提示、`result=0` 不附加提示、`0x8001` 同样生效
- **0x0200 位置汇报**：真实帧整帧反解（含 `7D01` 转义还原）、
  经纬度/速度/方向/BCD 时间逐字段比对、状态位拆解、
  附加项 `0x01`/`0x02`/`0x12`/`0x30`/`0x31`/`0xE1` 各项取值、
  附加项长度越界与只剩 1 字节的报错
- **808 全量消息体**（102 项）：50 个消息 ID 逐个构造消息体，断言关键字段取值，
  含 0x0107 真实帧全字段、0x0704/0x0400 递归展开、0x8108 包长一致/不一致两种标注、
  RSA e/n 越界、批量类元素越界、空消息体类带多余字节报错、未收录类型仍走兜底
- **桌面版模式**（14 项）：未注入时行为与浏览器版一致、注入后平台地址拼接
  （尾斜杠 / 已含完整路径 / 手动填值优先）、跨域外链转 `/__proxy` 而同源与相对地址不转、
  非法地址兜底、撤掉注入后回退

## 六、和 `../jt808_debugger/` 的区别

| | `jt808_debugger`（旧） | `jt808_offline`（本工具） |
|---|---|---|
| 运行方式 | Python 起 TCP 服务 + 网页 | 双击 exe（或双击 index.html） |
| 依赖 | Python 3 | 无（exe 自带运行时） |
| 需要设备连本机 | **是** | 否 |
| 用途 | 完整收发联调 | 拼报文 / 解报文 / 经平台下发 |

`jt808_debugger` 留着的原因：以后设备能连上本机了，做完整握手联调还是它方便。
设备连不上时，用本工具。
